# Правила ведения раздела

Правило действует для всех изменений в папке "Запрос цен" и обязательно к выполнению в каждой сессии работы с документацией. Машинная версия правила - в `AGENTS.md` в корне репозитория.

## 1. Обязательный цикл

**Перед изменением**

1. Прочитать `Changelog.md`, раздел "Текущее состояние".
2. Проверить, не описан ли вопрос в ТД складов. Если описан - не дублировать, дать ссылку.
3. Определить уровень пирамиды, к которому относится изменение: обзор → роль/сценарий → механика → данные/код/права.
4. Сверить утверждения с кодом: репозиторий, ветка, коммит, модуль.

**После изменения**

1. Обновить `Changelog.md`:
   - добавить запись в "Историю изменений" (новые сверху);
   - перезаписать "Текущее состояние".
2. Указать в записи: дату, что изменено, зачем, на основании чего, какие файлы затронуты.
3. Для каждой затронутой страницы добавить блок "Было → Стало".
4. Если изменение основано на коде - указать репозиторий, ветку, коммит и модуль.
5. Остатки и расхождения занести в "Открытые вопросы" changelog.

Без обновления changelog изменение считается незавершённым.

## 2. Что фиксировать в changelog

- **Структурные изменения:** новые страницы, слияния, переименования, удаление разделов.
- **Содержательные изменения:** новые механики, статусы, поля, методы.
- **Актуализацию:** изменение поведения после доработок, новые поколения документов, изменение кода.
- **Исправления:** неверные факты, битые ссылки, устаревшие названия.
- **Открытые вопросы и расхождения:** всё, что не удалось подтвердить кодом или ТД складов.

## 3. Формат записи

```markdown
### дд.мм.гггг - Краткая тема

**Что сделано**
- ...

**Было → Стало**
- `<страница>`: было ... → стало ...

**Основание**
- Код: репозиторий, ветка, коммит, модуль.
- ТД складов: раздел, версия.
- Заметки/совещания: ссылка.

**Файлы**
- ...

**Что не делали**
- ...

**Следующий шаг**
- ...
```

Запись должна позволять другому человеку понять, что изменилось и где это проверить, без чтения всей переписки и без диффа.

**Внутренние блоки.** "Было → Стало" и "Что не делали" нужны для контроля изменений внутри команды. При переносе changelog в sabydoc эти блоки не публикуются.

## 4. Актуальное состояние

В "Текущем состоянии" всегда должны быть:

- дата актуальности;
- проверенные ветки и коммиты;
- таблица разделов со статусом: `Готово`, `В работе`, `Заглушка`, `Устарело`;
- список открытых вопросов;
- явное указание, что проверено по коду, а что - только по документации.

Состояние перезаписывается, история - только дополняется.

## 5. Границы с ТД складов

- В разделе торгов: торг, связь с документом, лот и позиции лота, участники, заявки, цены, статусы торговой процедуры, победители, лучшие предложения, реестры, статистика.
- В ТД складов: документ, номенклатура документа, контакты, вложения, регламент и фазы, ЭДО/email/мессенджеры, СВРД, интерфейс карточки.
- Ссылки на склады - только на точки стыка. Массовые ссылки и повторное описание полей документа не допускаются.

## 6. Целевая структура раздела

| Уровень | Страница | Главный вопрос |
| --- | --- | --- |
| 1 | `Описание.md` | Зачем торги в Запросе цен, границы, участники, сквозной сценарий |
| 2 | `Алгоритмы и процессы.md` | Публикация → приём заявок → завершение → победитель → итоги |
| 3 | `База данных.md` | Что торги хранят у себя и чем связаны с документом |
| 3 | `Организация кода.md` | Точки входа, ORX-объекты, модули, репозитории |
| 3 | `Архитектура интерфейса.md` | Торговая часть в UI и источники данных |
| 3 | `Подсистема распределения прав.md` | Зоны доступа, роли, закрытый запрос цен |
| 4 | `Changelog.md` | История и актуальное состояние |
| 4 | `Правила ведения раздела.md` | Правила ведения раздела |

Роли покупателя и поставщика описываются подразделами внутри страниц, а не отдельными подсистемами.

Структуру страницы "Описание" сверяем с шаблоном "Шаблон базы знаний разработки прикладного продукта": Задачи → Концепт решения → Декомпозиция → Схема взаимодействия сервисов, базовых сущностей → Информационная модель. Дополнительные разделы - только если без них непонятно.

В корне раздела остаются только актуальные страницы. Устаревшие страницы и папки переносятся в `Архив/` и не удаляются: архив нужен для сверки и истории.

## 7. Пирамида Минто

Страница начинается с ответа, а не с предыстории:

1. Тезис - сразу ответ, без служебной подписи "Ключевой тезис".
2. Аргументы - 3-5 пунктов.
3. Детали - механики, данные, код.
4. Ссылки - где смотреть дальше.

Технические детали не поднимаются в "Описание". В "Алгоритмах" указываем методы БЛ/ORX, но не внутренние методы Python-модулей. Пошаговые вызовы и маппинги полей не выносим.

**Шапка страницы.** Блок "Кто читает / Условие присутствия / Цель документа" в документ не пишем, несмотря на шаблон. Страница начинается с заголовка и тезиса; служебную подпись "Ключевой тезис" тоже не пишем.

**Без дублей.** Одна мысль - в одном месте. Если тезис уже прозвучал, ниже раскрывайте только новое: механизм, данные, исключения. Не пересказывайте его другими словами.

**Типографика.** Кавычки только прямые. Длинные тире не используем, вместо них дефис.

**Без служебных разделов.** В страницах не пишем разделы "Что описывает этот раздел", "Перекрёстные ссылки", "Служебные разделы". Ссылки даются по месту.
