# Алгоритмы и процессы

Закупка в торгах проходит по сценарию: проекция документа → приём заявок → завершение приёма → выбор победителя → итоги. Публикация в Saby Trade зависит от регламента. Если в нём есть прохождение "Публикация в Saby Trade", торг показывается в мониторинге закупок, поставщики находят его через поиск и подают заявки. Если прохождения нет, участвуют только приглашённые поставщики. Покупатель и поставщик участвуют в одном процессе с разных сторон; их действия описаны внутри шагов.

Поля документа, номенклатура, контакты, вложения, каналы доставки и интерфейс карточки описаны в [ технической документации складских документов по Запросу цен](https://link.saby.ru/page/kbase_entity/01a9e45d-b671-4ebb-b9af-b599b21c8a4e?folderId=91b04551-1630-4733-a720-ba4ffad14655). Здесь описана логика приложения Saby Trade.

## 1. Проекция документа в торг

При создании черновика документа в сервисе торгов TenderWS создаётся черновик торга. Связь хранится в `tender2uuid`: `uuid` - идентификатор документа, `tenderid` - торг, `doc_type` - `quote_request_out`.

Лот и позиции формируются при публикации. Данные документа переносятся в `lot` и `lotitem`:

| Поле документа | Поле торга |
| --- | --- |
| `Номенклатура.Наименование` | `lotitem.name` |
| `ВходящееНаименование.Наименование`, если нет `Номенклатура.Наименование` | `lotitem.name` |
| `КоличествоПоУпаковке`, иначе `Количество` | `lotitem.quantity` |
| `ЦенаПоУпаковке`, иначе `Цена` | `lotitem.price` |
| `Номенклатура` | `lotitem.nomenclature_id` |
| `НазваниеЕИ` | `lotitem.okei_name` |
| `НоменклатураДокументаРасш.Комментарий` | `lotitem.addinfo` |
| `Номенклатура.НомНомер` | `lotitem.extra_info->nom_number` |
| `НоменклатураДокументаРасш.Комментарий` | `lotitem.extra_info->comment` |
| `НоменклатураДокументаРасш.ЕИУ` | `lotitem.extra_info->НоменклатураДокументаРасш.ЕИУ` |
| `КоличествоПоУпаковке` | `lotitem.extra_info->КоличествоПоУпаковке` |

Идентификатор торга хранится в параметрах документа.

Сохранение заявок и публикация выполняются асинхронно. Чтобы не обновлять одну запись торга или заявки одновременно, используются рекомендательные блокировки по uuid документа. Это нужно, когда одновременно срабатывают публикация и сохранение, а также множественная отправка и быстрый ответ поставщика.

## 2. Публикация и статусы

Торг создаётся вместе с документом и до публикации остаётся черновиком. Публикация выводит его в реестр торгов Saby Trade, чтобы поставщики нашли закупку через поиск, и переводит в приём заявок.

Публикацию выполняет прикладная суперфаза `STPublishSPhase` из EDO-репозитория `sbis-tender-sphases`. В `OnCloseEvent` она асинхронно вызывает `ExecuteSTSuperPhase` у объекта торгов, который переводит торг в "Приём заявок" и размещает закупку в мониторинге торгов. Суперфаза добавляется в документ по событию `online.quoterequestoutaddphases` обработчиком `TenderQuoteRequestOut.AddPhases`.

Исходный код суперфазы: [sbis-tender-sphases](https://git.sbis.ru/edo/core/-/tree/HEAD/sbis-tender-sphases). Идентификатор суперфазы - `ad8b81efbb9349a9bba2e07fa50f86d8`; в ленте событие называется "Опубликовано в Saby Trade".

| Статус торга | Что означает |
| --- | --- |
| Черновик | Торг создан, на площадке не виден |
| Приём заявок | Торг опубликован, поставщики могут подавать заявки |
| Рассмотрение заявок | Приём завершён, покупатель работает с предложениями |
| Завершён | Победитель выбран, итоги зафиксированы |
| Отменён | Закупка отменена |
| Не состоялся | Закупка не собрала участников или заявок |

**Закрытый запрос цен.** Признак закрытого торга хранится в `tender_ext.extra_data` под ключом `is_private_participation` и проверяется в сервисе торгов TenderWS и tender-worker. Проверка не даёт закрытому торгу попасть в открытый поиск и индексацию и ограничивает доступ пользователям, не связанным с торгом. При множественной отправке документа без публикации торг переходит в приём заявок, но в открытом поиске не показывается.

| Торг | ES | Открытый поиск | ClickHouse |
| --- | --- | --- | --- |
| Открытый | `tender`, `tender_actual` в статусе "Приём заявок" | Виден всем | Попадает |
| Закрытый | `tender`, `tender_actual` в статусе "Приём заявок", с `is_private_participation = true` | Виден организатору и приглашённым | Не попадает |

В ES закрытый торг не выносится в отдельный индекс. Он хранится в общем индексе `tender` (и `tender_actual` для статуса "Приём заявок") как обычный документ, но с полем `is_private_participation = true`. Поле заполняется из `tender_ext.extra_data`. В запросах оно сравнивается с `organizer_client_id` - идентификатором клиента-организатора: закрытый торг проходит фильтр, только если `organizer_client_id` совпадает с текущим клиентом. Для остальных клиентов такой торг отфильтровывается. В ClickHouse закрытые торги исключены из статистики.

## 3. Приём заявок

### Добавление поставщика

При создании документа поставщиков добавляют в торг объектом `TenderParticipantEdo`. По `Лицо1` из документа получают контрагента и проверяют ИНН и признак ЭДО. ИНН нужен, чтобы сопоставить или создать организацию в `participant`; без ИНН сопоставление невозможно. Признак ЭДО показывает, можно ли отправлять приглашение по ЭДО; если поставщик отключил ЭДО, приглашение идёт по email. Затем через `TenderParticipant.UpdateParticipant` сопоставляют или создают организацию в `participant` и сохраняют заявку в `result`. `Лицо1` сохраняется в `result.extra_info` для последующего сопоставления.

### Каналы

| Канал | Что происходит в торгах |
| --- | --- |
| ЭДО | `TenderQuoteRequestIn.Create` создаёт заявку, при отправке ставится `result.invite = 2` или `4`, `send_type = edo`, `edo_transfer = true` |
| Email и СВРД | `TenderQuoteRequestIn.SaveOfferByEmail` сохраняет ответ, `send_type = email`; аккаунт поставщика не нужен |
| Мессенджер | Поставщик переходит по приглашению и подаёт заявку |
| Поиск торгов | Поставщик находит опубликованный торг сам, `result.invite = -2` |
| Ручной ввод | Покупатель вводит цену за поставщика, `result.invite = 3` |

Каждый канал приводит к одной заявке в `result` и позициям в `resultitem`.

### Статусы заявки

| Код | Статус | Что означает |
| --- | --- | --- |
| 0 | Черновик организатора | Заявку создал покупатель |
| -2 | Нашёл сам | Поставщик не получил приглашение, но нашёл торг и подал заявку |
| -1 | Черновик участника | Поставщик начал оформлять заявку |
| 1 | Приглашение отправлено | Приглашение ушло по email или поставщик подключён к ЭДО |
| 2 | Заявка отправлена | Поставщик отправил предложение |
| 3 | Заявка введена покупателем | Цены ввёл покупатель за поставщика |
| 4 | Отказ | Поставщик отказался от участия |

### Ручной ввод цены

Если поставщик не ответил, покупатель вводит цены за него. Сумма сохраняется в `result.extra_info->customer_amount`, комментарий - в `customer_comment`, дата изменения - в `change_datetime`. Если поставщик позже пришлёт своё предложение, оно перезапишет ручной ввод.

## 4. Завершение приёма заявок

Завершением срока приёма заявок управляет этап документа, помеченный прикладной опцией "Прием заявок в закупке" `requestReceivingToggle` в регламенте Запроса цен. Эта опция доступна у этапов только для типа документа PriceRequestOut.

Срок окончания приёма заявок хранится в `ДокументРасширение.Параметры` под ключом `end_order_date`. Что происходит на стороне документа и на стороне торгов:

| Событие | Online (документ) | TenderWSRU |
| --- | --- | --- |
| Наступление этапа "Прием заявок" | Регламент начинает этап; срок задан формулой `ПолучитьДатуОкончанияПодачиЗаявок(ДокументРасширение)`, значение берётся из `ДокументРасширение.Параметры.end_order_date` | Обработчик события `Document.StateChanged` видит опцию у этапа `requestReceivingToggle` и вызывает `Docflow.RecalcDeadline`; торг остаётся в "Приёме заявок" |
| Редактирование даты "Приём заявок до" | Новое значение сохраняется в `ДокументРасширение.Параметры.end_order_date` | Обработчик сохранения видит новый `DocExtParamsRecord.end_order_date` и вызывает `Docflow.RecalcDeadline`; в DWC обработчик переключения статуса торга `AppReceivingEnd` переносится на новую дату |
| Наступление даты окончания | Документ переходит на этап регламента, указанный в настройке "при нарушении срока запускать" (в инсталляционном регламенте это этапа - "Определение победителя") | параллельно отложенный вызов DWC с кодом `AppReceivingEnd` вызывает `TenderQuoteRequestOut.SetApplicationExaminationStatus`; торг переходит в "Рассмотрение заявок" |
| Уход с этапа "Прием заявок" | Документ переходит на выбранный следующий этап | Обработчик `Document.StateChanged` вызывает `Tender.change_tender_stateL`; торг переходит в "Рассмотрение заявок", `end_order_date` выставляется на текущий момент, DWC-вызов окончания приёма отменяется |



### Формула срока этапа

На этапе "Прием заявок" срок задан формулой:

```text
return ПолучитьДатуОкончанияПодачиЗаявок(ДокументРасширение);
```

Функция [ПолучитьДатуОкончанияПодачиЗаявок](https://saby.ru/help/regulations/spk/functions/regulations_handlers/get_request_receiving_end_date) возвращает срок выполнения этапа из `ДокументРасширение.Параметры` (поле `end_order_date`) в формате `ГГГГ-ММ-ДД ЧЧ:ММ:СС`. На этапе включена настройка "Прием заявок в закупке требуется".

`Docflow.RecalcDeadline` пересчитывает формулу, чтобы переход регламента произошёл в новую дату.

### Доотправка после окончания приёма

Кнопка доотправки доступна и после окончания приёма заявок до завершения ДО Запроса цен. Если этап "приёма заявок" уже прошел, то при доотправке устанавливается новый срок приёма заявок: текущий момент + 30 дней.
Торг возвращается в приём заявок, обработчик окончания приёма ставится заново, а поставщик может ответить на повторное приглашение.

## 5. Выбор победителя

Победитель выбирается на этапе, помеченном настройкой "Выбор победителя в закупке" (`winnerChoiceToggle`). Это прикладная настройка доступна только для Запроса цен, как и `requestReceivingToggle`.

На ДЗЗ этапа покупатель видит список участников и выбирает одного или нескольких. Список получают методом `TenderParticipantEdo.ListParticipant`. Идентификаторы победителей передаются в `winner_org_ids` и обрабатываются `TenderQuoteRequestOut.WinnersSelected`.

Правила:

- выбранный поставщик получает `result.admitted = true` и `result.apprating = 1`;
- если победителей несколько, лучшее предложение выбирается по приоритету: больше позиций с ценами, затем меньшая суммарная цена;
- после прохождения этапа в заявке победителя выставляется `result.extra_info->prefered_winner = 1`; признак сохраняется, чтобы цена победителя и списки брали готовый результат выбора, а не пересчитывали его заново.

### Смена статуса торга при выходе с этапа

- нейтральный завершающий и положительный переходы переводят торг в рассмотрение заявок;
- отрицательный переход отменяет торг и сбрасывает выбранных победителей;
- переход "Переназначить" статус торга не меняет.

## 6. Лучшие предложения и итоговая цена

Отчёт "Лучшие предложения" показывает выгодные предложения среди всех поставщиков. По каждой позиции выбирается предложение с минимальной ценой; при равенстве - предложение поставщика, ответившего по большему количеству позиций; затем - лучшее предложение по всем позициям. Отчёт строит `TenderQuoteRequestOut.GetBestOffers`.

Итоговая цена при нескольких победителях определяется по приоритету: больше позиций с ценами, затем меньшая суммарная цена. Цена показывается в реестрах документов, в реестре "Закупаем" и в виджете "Закупали".

## 7. Основные обработчики

| Процесс | Объект ORX | Точка входа |
| --- | --- | --- |
| Создание, удаление, фазы торга | `TenderQuoteRequestOut` | события `online.quoterequestout*` |
| Ответ поставщика по ЭДО | `TenderQuoteRequestIn` | события `online.quoterequestin*` |
| Подача заявки из карточки торга | `TenderParticipantOffer` | `TenderParticipantOffer.Create` |
| Выбор победителя | `TenderQuoteRequestOut` | `TenderQuoteRequestOut.WinnersSelected` |
| Лучшие предложения | `TenderQuoteRequestOut` | `TenderQuoteRequestOut.GetBestOffers` |
